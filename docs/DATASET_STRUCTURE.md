# 数据集逻辑结构

## 1. Scenario

`Scenario` 表示相对稳定的线路与通信环境，包括：

- 线路空间范围；
- AP 数量、位置、间距、高度和天线参数；
- OBM 布局和列车长度；
- 载波频率；
- 路径损耗、阴影和多径参数域；
- 接收机报告参数；
- 参数来源类型及适用边界。

它不是“所有可能线路”的穷举，而是有依据的有限场景族。

## 2. Run

`Run` 表示一趟从起点到终点的完整运行，包括：

- 时间—位置—速度轨迹；
- 一次冻结的随机传播世界；
- 健康或故障状态；
- 故障目标、故障参数名、数值及物理单位；
- 生成器版本、配置哈希和随机种子；
- 配对健康运行标识；
- 官方数据划分。

同一个 Scenario 下可以有多条 Run，用于覆盖不同速度轨迹、随机实现和故障状态。

### 第一版 Run 约束

第一版采用便于解释、验证和单标签分类的最小约束：

```text
一条 Run
├── 一个 target_ap_id
├── 一种状态（健康或五类单故障之一）
└── 一个主要 Sample
```

故障 Run 中只有 `target_ap_id` 对应设备被设置为故障，其他 AP 保持健康。
“全链路功率衰减”指目标 AP 两副天线共用射频链路的衰减，不表示整条线路
全部 AP 同时衰减。健康 Run 也指定目标 AP，以便与故障 Run 生成结构一致
的对照样本。

多目标、多故障和一条 Run 提取多个 Sample 都是合理扩展，但不属于第一版
正式分类契约。

## 3. Sample

`Sample` 是从 Run 中围绕目标 AP 截取的诊断窗口。它保存：

- `sample_id` 和目标 AP；
- 上下文窗口范围；
- 健康/故障标签；
- 故障目标以及带物理单位的故障参数；
- 对应观测文件；
- 可选的质量标志。

第一版每条 Run 只产生一个主要 Sample。Sample 的窗口由列车参考点
（默认 `OBM-front`）进入和离开目标 AP 上下文区间的时刻确定。车尾
`OBM-rear` 具有纵向偏移，因此同一时刻两套 OBM 的 `position_m` 可以不同，
且不要求每一行观测位置都落在列车参考点的窗口边界内。

一个 Sample 不是“一条目标 AP 曲线”。它应同时保存：

- `target_ap_id` 的观测；
- 至少一个相邻候选 AP 的上下文观测；
- `OBM-front` 与 `OBM-rear` 两套接收端观测；
- 每个 OBM 当时的服务 AP 状态。

## 4. Observations

`Observations` 不是第四级编号，而是 Sample 内部的逐点长表。每一行对应一个报告时刻下某个 AP—OBM 候选链路。多 AP、双 OBM 场景中，同一时刻可以有多行。

原始长表是权威表示；补零+掩码或重采样矩阵属于派生的模型输入，不应覆盖原始数据。

### 三类 AP 字段

- `target_ap_id`：这条 Run/Sample 要诊断的目标 AP，整条样本内保持不变；
- `ap_id`：当前 Observation 所属的候选 AP；
- `serving_ap_id`：当前时刻、当前 OBM 实际接入的 AP；
- `is_serving`：`ap_id == serving_ap_id` 的冗余布尔标志，便于筛选与校验。

同一时刻、同一 OBM 可以有多条候选 AP Observation，但只能有一条
`is_serving=true`。

## 5. 防止数据泄漏

- 不逐行随机切分；
- 第一版每条 Run 只有一个 Sample；扩展为多 Sample 后，同一 Run 的所有 Sample 仍必须放在同一集合；
- 配对健康/故障 Run 放在同一集合；
- `test_id` 按 Run 分组，用于测试已知 Scenario 下的新运行；
- `test_ood` 按 Scenario 分组，用于测试未见线路、AP 布局和传播环境；
- 所有官方划分随版本冻结并发布。
